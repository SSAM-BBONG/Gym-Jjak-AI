# 📡 SSE 델타 어절 분할 변경 — Spring 팀 전달 사항

- 작성일: 2026-07-25
- 상태: FastAPI 측 구현·리뷰 완료, Spring 측 검토·반영 필요
- 범위: `POST /api/v1/chatbot/messages`의 SSE `delta` 이벤트 전송 방식 변경. 엔드포인트 경로, `delta`/`done`/`error` 이벤트 스키마 자체는 변경 없음.
- 관련 문서: [ARCHITECTURE.md § 📡 SSE 스트리밍 응답](ARCHITECTURE.md) (이번 변경 반영됨), FastAPI 저장소 커밋 범위 `52f33a5..b7baf2e`

## 🧭 무엇이 바뀌었나

프론트에서 "delta 하나가 문장 2개 분량으로 너무 크게 온다, 타이핑 효과를 적용하기 어렵다"는 요청이 있었다. 원인은 `agent_node`/`rag_node`가 Gemini 스트리밍 청크를 그대로 큐에 넣고, `greeting_node`/`reject_node`/`routine_node`는 완성된 답변 전체를 한 번에 큐에 넣기 때문이었다.

`ChatbotService.chat()`이 큐에서 꺼낸 텍스트를 **어절(공백) 단위로 재분할**해서 `delta`로 내보내도록 바꿨다. `delta` 이벤트의 페이로드 형식(`{"text": str}`)은 그대로이고, **한 요청당 delta 이벤트 개수만 늘어난다.**

아래 3가지는 이번 변경으로 Spring/프론트 쪽에서 함께 검토·반영이 필요한 사항이다.

---

## 1. 델타가 여전히 "버스트"로 도착한다 — 타이핑 효과는 수신 측 페이싱이 필요

**문제:** FastAPI가 어절 단위로 델타를 쪼개긴 했지만, 전송 자체는 페이싱 없이 즉시 순차 `yield`된다(`for word in ready_words: yield ...`에 지연이 없음). 문장 하나 분량의 Gemini 청크가 도착하면 거기서 나온 어절 10~20개가 사실상 같은 순간에 FastAPI → Spring으로 도달한다.

**영향:** Spring이 SSE로 받은 delta를 받는 즉시 기존 WebSocket으로 그대로 릴레이하면, 프론트에도 여전히 "우르르 몰려서" 도착한다 — 델타 크기만 작아졌을 뿐 체감 개선이 없을 수 있다.

**대응 필요 사항 (Spring/프론트 팀 결정 필요):**
- 실제 타이핑 애니메이션 효과를 원한다면, 델타를 받는 즉시 렌더링하지 말고 **큐에 쌓아 뒀다가 일정 간격(예: 20~40ms)으로 하나씩 소비**하는 로직이 필요하다.
- 이 페이싱을 어느 계층에 둘지(Spring 릴레이 계층 vs 프론트 렌더링 계층)는 Spring/프론트 팀이 결정할 사항이며, FastAPI 쪽에는 페이싱을 추가하지 않았다(응답 완료 지연·타임아웃과 상호작용이 생기므로 서버 측 `sleep` 방식은 채택하지 않음).

## 2. 요청당 SSE 이벤트 수가 크게 늘어난다

**문제:** 기존에는 `routine_node`/`reject_node`/`greeting_node` 라우트가 delta 이벤트 1건만 보냈지만, 이제 같은 라우트도 답변 길이에 비례해 델타가 수십 건 나갈 수 있다. `agent_node`/`rag_node`도 기존 대비 세분화되어 이벤트 수가 늘어난다.

**영향:** 한 요청당 WebSocket 프레임 릴레이 횟수가 같은 배수로 늘어난다. 델타 이벤트마다 로깅·메트릭을 남기는 코드가 있다면 로그량도 비례해서 증가한다.

**대응 필요 사항:**
- Spring이 delta 이벤트를 릴레이할 때 이벤트 단위로 로깅/메트릭을 남기고 있는지 확인하고, 필요하면 샘플링하거나 요약 로깅으로 조정한다.
- WebSocket 프레임 전송 비용이 문제가 될 수준인지 부하 테스트로 확인이 필요하다(FastAPI 저장소 밖 사항이라 이번 변경에서 직접 측정하지 않았다).

## 3. delta 0건으로 스트림이 끝나는 경우, `done.answer`를 반드시 표시해야 한다

**문제:** LLM이 빈 텍스트를 반환하는 경우(안전 필터 차단, `MAX_TOKENS` 등) `agent_node`/`rag_node`는 큐에 아무 델타도 넣지 않는다(`if chunk.delta:` 가드). 이 경우 `delta` 이벤트가 0건인 채로 `done` 이벤트만 오고, `done.answer`에는 대체 문구(`"죄송합니다, 지금은 답변을 생성하지 못했습니다."`)가 채워진다.

**기존 계약:** ARCHITECTURE.md는 "Spring은 이미 흘려보낸 delta 뒤에 `done.answer`를 다시 이어붙이면 안 된다(중복 표시 방지)"고 명시한다. 이 규칙만 그대로 따르면, delta가 0건인 요청에서는 **아무것도 표시되지 않는 빈 말풍선**이 생긴다.

**대응 필요 사항 (필수):**
- Spring/프론트는 **해당 요청에서 delta를 한 건도 받지 못한 채 `done`이 도착한 경우, `done.answer`를 화면에 표시**해야 한다.
- 이 조건은 신규 로직이 아니라 원래도 존재하던 예외였으나(이번 변경 이전부터), 이번에 문서화가 누락돼 있던 것을 함께 정리했다. Function Calling 중간 턴이 남긴 델타가 최종 `done.answer`에 포함되지 않는 경우도 이론상 있을 수 있다(드묾) — 이 역시 `done.answer`를 최종 진실 소스로 신뢰해야 하는 이유 중 하나다.

---

## ✅ 변경되지 않은 것 (참고)

- `delta`/`done`/`error` 이벤트 스키마, HTTP 경로, 인증 방식은 그대로.
- "delta 최소 1개 이상 → done" 순서 보장은 유지된다(단, 위 3번처럼 LLM이 빈 응답을 낸 예외적 경우는 원래도 있던 예외).
- 에러 통일 원칙(모든 실패가 `error` 이벤트로 변환)은 그대로.
